# ADR-0002: Content files are YAML and Markdown whose zod schema output is the file's own shape

- **Status:** accepted
- **Date:** 2026-09-13
- **Related:** PROMPT.md sections 9.1, 13; ideas/solutions/content-pipeline.md, ideas/solutions/plugin-architecture.md

## Context
Content (packs, realms, skills, oaths, classes, enemies, items, cards, challenges) and tunables (`config/balance.yaml`)
must be hand-authored, validated, generated by the Forge later, and loaded by the server. The pre-build seed files
mixed conventions: most keys were snake_case, but io test cases used `expectedStdout`; `balance.yaml` declared the
key `version` twice (invalid YAML); the Artificer's abilities sat inside `class.yaml` although sections 6 and 13
describe a separate `abilities.yaml`.

## Options considered
1. **snake_case files, camelCase TypeScript types** with a transform in the loader. Idiomatic TypeScript inside the
   engine. Two shapes to keep in mind, a mapping layer to maintain in both directions (the Forge writes files), and
   error messages that name keys the code never uses.
2. **One shape.** Files use snake_case keys, and the zod schema's output type uses the same keys. No mapping layer;
   what you read in YAML is what you read in code and in validation errors. Some snake_case properties in TypeScript.
3. **camelCase files.** One shape too, but unusual in hand-written YAML and a rewrite of every seed file.

## Decision
Option 2, with these rules:
- Schemas are strict: unknown keys are errors, so a typo such as `prerequisite:` fails loudly with a line number.
- Data is YAML; prose is Markdown (`prompt.md`, `hints.md`, `lesson.md`, `explanation.md`, `lore.md`). `hints.md`
  has exactly four levels separated by lines containing only `---`.
- Ids are lowercase segments joined by `.` or `-`; tags may also contain `+` and `#`. Realms and skills are open
  (data); languages are a closed list because each needs a runner.
- One enemy or item per file, named `<id>.yaml`; class folders are named after the class id; challenges live in
  `challenges/<realm>/<folder>/` where the realm folder must match the manifest.
- io test cases use `expected_stdout`, may use a `generator` for large stdin, and hidden files may hold
  `reserve: true` cases that an enemy's Edge Case move adds mid-fight.
- JSON configuration edited by the app (`config/ai.json`, M2) keeps JSON's camelCase convention.

## Consequences
- Seed changes made to fit the schemas: `expectedStdout` became `expected_stdout`; the balance progression section
  became `character_version`; Artificer abilities moved to `abilities.yaml` with `implemented: false` until the
  engine supports them; `oaths.yaml`, two item files, enemy ASCII art, a Tally Wisp `explanation.md`, and two reserve
  test cases were added.
- The loader (`packages/content-tools/src/loader/`) reports every problem with file and line, and
  `pnpm content:validate` adds cross-reference, graph, test-count, and execution checks.
- Code that touches content reads snake_case properties such as `manifest.tests.entry`; engine state and API DTOs
  use camelCase because they are not files.
